## 3. 项目代码

文件：`W9/homework/lbgs-1/queue_tasks.py`

```python
from collections import deque
import heapq

def max_sliding_window(nums, k, trace=None):
    if k <= 0 or not nums:
        return []
    dq = deque()                       # 存的是下标，不是数值
    result = []
    for i, x in enumerate(nums):
        if dq and dq[0] <= i - k:      # 队头已滑出窗口
            dq.popleft()
        while dq and nums[dq[-1]] <= x:  # 新元素更大，队尾小元素永无出头之日
            dq.pop()
        dq.append(i)                   # 存下标，才能判断是否过期
        if i >= k - 1:
            result.append(nums[dq[0]])  # 队头就是当前窗口最大值
        if trace is not None:
            trace.append((i, x, list(dq), list(result)))
    return result

def schedule_tasks(priorities, log=None):
    heap = []
    for i, p in enumerate(priorities):
        heapq.heappush(heap, (p, i, f"任务{i}"))   # (优先级, 到达序号, 任务)：序号保证稳定
    order = []
    while heap:
        p, i, task = heapq.heappop(heap)
        order.append((p, i, task))
    return order
```

三处关键点：

1. `deque` 里存**下标**而不是数值——只有下标才能判断 `dq[0] <= i - k`（是否过期）。
2. `while` 而不是 `if`：新元素可能一次弹掉队尾多个更小的元素。
3. 堆元素是 `(优先级, 到达序号, 任务名)` 三元组——第三项只用于"同优先级按到达顺序"，
   不加序号时相同优先级下 Python 会比较第三项（演示见第 5 节，会抛 `TypeError`）。

## 4. 滑动窗口最大值：逐步追踪

`nums = [5, 3, 4, 1, 2]`，`k = 3`，脚本实际输出（`show_trace`）：

| i | x | dq（存索引） | result |
|:---:|:---:|:---|:---|
| 0 | 5 | `[0]` | `[]` |
| 1 | 3 | `[0, 1]` | `[]` |
| 2 | 4 | `[0, 2]` | `[5]` |
| 3 | 1 | `[2, 3]` | `[5, 4]` |
| 4 | 2 | `[2, 4]` | `[5, 4, 4]` |

结果 `[5, 4, 4]`，与暴力法 `max(nums[i:i+k])` 核对一致。

对照课件表格的一个小差异：课件在 `i=4` 处写的是 `dq=[2,3,4]`，实跑是 `[2,4]`。
原因是 `nums[3]=1` 比新元素 `2` 小，`while` 循环会把它弹掉（填 3 意味着保留了比 2 小的 1，
违反"单调递减"）。两种写法最终结果都是 4，不影响答案，但 `[2,4]` 才符合代码逻辑。

- 两个 `p=1` 的任务按到达顺序 1 → 3 出堆，这就是 `(p, 序号, 任务)` 里序号的作用。
- 注意第 4 次入堆后堆内数组是 `(1,1),(1,3),(4,2),(3,0)`——**看起来乱序**。
  `heapq` 只保证 `heap[0]` 最小，整体不是排序数组；需要全序时得另外 `sorted`。
- 反例（不加序号）：`heapq.heappush(heap, (2, {"name": "任务0"}))` 推两次后出堆，
  抛 `TypeError: '<' not supported between instances of 'dict' and 'dict'`
  ——相同优先级时 Python 会比较元组第三项。脚本里 `show_tiebreak_problem()` 复现了这一错误。

## 6. 思考题：为什么老元素"永无出头之日"

新元素更大时，它比老元素**更晚**滑出窗口，又比老元素**更大**；因此在老元素还留在窗口里的每一个时刻，
新元素都在同一个窗口内且更大——老元素不可能成为最大值，可以直接弹掉。

和 FIFO 不矛盾：单调队列不是"公平排队"的结构，它只保留"还有希望成为答案"的候选，
本质是按"能否当最大值"淘汰元素，deque 只是提供了两端增删的容器；普通队列（FIFO）保证的是顺序，两者目的不同。

## 8. 复杂度对比（`--bench`）

同一随机数组、同样窗口，单调队列与暴力法的实测耗时：

| n | k | 单调队列 O(n) | 暴力法 O(nk) |
|:---:|:---:|:---:|:---:|
| 2 000 | 50 | 0.610 ms | 1.279 ms |
| 20 000 | 50 | 4.750 ms | 10.833 ms |
| 20 000 | 500 | 4.874 ms | 85.812 ms |

`n` 固定为 20000 时，`k` 从 50 涨到 500（×10），暴力法耗时 10.8 → 85.8 ms（约 ×7.9），
单调队列几乎不变（4.75 → 4.87 ms）：每个下标最多入队、出队各一次，与 `k` 无关。

## 9. 反思

优先队列和"手动排序"最大的区别是**什么时候排序、为谁排序**：`sorted` 要先攒齐全部任务、一次性排出全序（O(n log n)），
中途来了高优先级任务只能重排；`heapq` 每次插队只要 O(log n)，随时可以加入新任务、每次都只取"当前最该做的那个"，
不需要全序——就像急诊分诊，看的是"下一个最紧急"，而不是给所有病人排一张总表。
